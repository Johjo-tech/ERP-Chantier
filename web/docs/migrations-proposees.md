# Migrations proposées (non appliquées en production)

La réécriture ne modifie **jamais** la production. Ces fichiers vivent dans
`web/supabase/propositions/`, sont appliqués à la base LOCALE par
`npm run base:locale`, et validés par les tests RLS marqués `[proposition]`.
Ils sont un **prérequis** à la mise en service de `web/` (DECISIONS D-018).

## Comment les appliquer (par un humain)

1. **Essai à blanc sur la production** (règle du dépôt) : le fichier encadré de
   `begin;` … `rollback;`, avec un `select` de contrôle avant l'annulation :
   ```sql
   begin;
   \i 20260925015000_peut_ecrire_ne_rend_jamais_null.sql
   select peut_ecrire('00000000-0000-0000-0000-000000000000'::uuid); -- attendu : false (et non NULL)
   rollback;
   ```
   Pour le n° 12, le contrôle qui porte : aucune facture ne doit changer de
   `reste` sans raison — `select count(*) from v_facture_solde where sens > 0
   and cle <> 'reprise' and acomptes = 0 and retenue = 0` avant et après, et
   `select sum(du), sum(credit) from v_facture_solde` (l'ancien total des
   impayés comptait les avoirs : l'écart attendu est leur crédit).
2. Puis, depuis la racine du dépôt, le canal qui marche (CLAUDE.md) :
   `supabase db query --linked -f <fichier>` et l'insertion dans
   `supabase_migrations.schema_migrations`. **Ces commandes sont bloquées pour
   l'agent** (`web/.claude/hooks/garde-prod.mjs`) : c'est volontaire.
3. Copier chaque fichier dans `supabase/migrations/` (racine) au moment de
   l'appliquer, puis `npm run db:types` et recopier `database.types.ts` dans
   `web/src/lib/` ; supprimer alors `web/src/lib/database.propositions.ts`.

## Vues refaites : l'essai à blanc qui porte (relecture 4, I6)

La production a divergé de la base locale (88 migrations passées par le
tableau de bord). Une vue refaite d'après un texte écrit en local peut, à noms
et types égaux, **démasquer** une colonne que la production masque — sans la
moindre erreur. Trois propositions refont une vue de production :

| N° | Vue | Garde dans le fichier |
|---|---|---|
| 12 | `v_facture_solde` | compare `pg_get_viewdef` en place à la définition de `20260101000000_base_schema_distant` (et à celle qu'elle pose) ; toute autre → `raise exception` |
| 20 | `v_salaries_annuaire` | idem, contre la définition de `20260921120000_le_dossier_rh_suit_le_droit_rh` |
| 25 | `v_bons_commande_terrain`, `v_bon_commande_lignes_terrain` | part de la définition VIVANTE et ne remplace que le filtre ; arrêt s'il n'y figure pas exactement une fois |

Les deux textes comparés passent par le **même serveur** (vues temporaires) :
le format de `pg_get_viewdef` ne fait donc pas de faux écart d'une version de
Postgres à l'autre. Un test (`politiques.essai.ts`, I6) refuse toute
proposition qui referait une vue de production hors d'une telle garde.

Sur la production, **avant** d'appliquer, par un humain :

```sql
-- 1. Relever les définitions vivantes (à garder dans le ticket).
select c.relname, c.reloptions, pg_get_viewdef(c.oid) from pg_class c
 where c.relname in ('v_facture_solde', 'v_salaries_annuaire', 'v_bons_commande_terrain', 'v_bon_commande_lignes_terrain');
-- 2. Essai à blanc : la garde s'arrête d'elle-même si la vue a divergé.
begin;
\i 20260926040000_le_solde_d_une_facture_dit_vrai.sql
\i 20260926060000_les_donnees_rh_restent_aux_rh.sql
\i 20260926102000_le_sous_traitant_ne_lit_que_ses_taches.sql
select c.relname, c.reloptions, pg_get_viewdef(c.oid) from pg_class c
 where c.relname in ('v_facture_solde', 'v_salaries_annuaire', 'v_bons_commande_terrain', 'v_bon_commande_lignes_terrain');
rollback;
```

Comparer les deux relevés colonne par colonne : seules doivent changer les
expressions que la proposition annonce (n° 12 : tout le calcul ; n° 20 :
`visite_medicale_date`, `visite_medicale_prochaine`, `notes` masquées ; n° 25 :
le filtre `est_membre` → `bon_lisible`) ; `reloptions` doit garder
`security_barrier=true` (n° 20, 25) ou `security_invoker=true` (n° 12). Si la
garde s'arrête : refaire le texte de la proposition depuis la définition
relevée en 1, jamais forcer.

## Essai sur une base neuve

`bash scripts/essai-base-neuve.sh [nom]` crée une base temporaire dans le
conteneur local (la base partagée n'est pas touchée), y rejoue les migrations
du dépôt, le rattrapage, puis **toutes** les propositions dans l'ordre — deux
fois, chacune devant rester rejouable —, charge le jeu d'essai, et supprime la
base (`GARDER=oui` pour l'inspecter). Passé sans erreur après la relecture 4
(D-SQL-08).

## Relecture 4 (D-SQL-01 à D-SQL-08)

Les propositions n'ayant jamais été appliquées en production, les constats
sont corrigés **dans les fichiers** plutôt que par des rustines : n° 4, 5, 6,
